# Архитектурный план: Supervisor и отказоустойчивые агенты (v2)

Текущая проблема заключается в том, что жизненный цикл агента (LLM Worker) жестко привязан к жизненному циклу HTTP-запроса (SSE-стрима). Если фронтенд отваливается — агент "умирает". Кроме того, агент иногда "слепнет" или зацикливается, и некому его поправить.

Чтобы решить эту проблему, предлагается перестроить архитектуру на паттерн **"Асинхронные воркеры + Supervisor + Event Sourcing"**.

## Основные изменения в архитектуре и устранение слабых мест

### 1. Внешний процесс-воркер (Celery / ARQ / Temporal)
Использование `BackgroundTasks` в FastAPI не дает настоящей отказоустойчивости, так как падение процесса убивает и фоновые задачи без возможности автоматического подхвата.
* **Решение:** Выделяем выполнение агента в **отдельный процесс-воркер** (с использованием очередей типа Celery, ARQ или Redis Queue). Это гарантирует, что если воркер упал (OOM, рестарт), задача останется в очереди или в статусе `running` в БД, и другой инстанс воркера сможет ее безопасно подхватить.

### 2. БД как источник истины (Event Sourcing) и Replay
Redis Pub/Sub работает по принципу "fire and forget". Если фронтенд отключился, события будут потеряны.
* **Решение:** Источником истины становится таблица `AgentTaskEvent` (поля: `task_id`, `sequence_number`, `event_type`, `payload`).
* Воркер **пишет событие в БД**, а затем кидает уведомление в Redis Pub/Sub (`task_id:new_event`).
* Когда фронтенд подключается, он запрашивает все события из БД (от начала или с последнего известного `sequence_number`), а затем подписывается на Redis для получения новых событий в реальном времени. Это гарантирует 100% возможность replay-я.

### 3. Защита от Race Conditions при рестарте
Когда несколько воркеров рестартуют и пытаются подхватить "осиротевшие" задачи со статусом `running`.
* **Решение:** Использовать транзакционные блокировки базы данных: `SELECT ... FOR UPDATE SKIP LOCKED` в PostgreSQL. Воркер берет задачу в "аренду" (lease) монопольно, исключая двойное выполнение.

### 4. Идемпотентность Tool Calls
Если воркер падает после вызова инструмента с побочным эффектом (например, оплата, отправка письма, сабмит формы), но до записи чекпоинта, рестарт приведет к повторному выполнению.
* **Решение:** Для всех инструментов с побочными эффектами (side-effects) вводится **Idempotency Key**. Воркер перед вызовом инструмента генерирует хэш (или UUID) шага и сохраняет его. Целевая система (или обертка инструмента) должна игнорировать повторные вызовы с тем же ключом.

### 5. Роль Supervisor и умное хэширование DOM
Для предотвращения зацикливаний и галлюцинаций вводится Supervisor. Его триггером выступает зацикливание действий (одинаковые вызовы) или отсутствие изменений на странице.
* **Кэширование:** Таблица `ResourceDomCache` (поля: `resource_domain`, `dom_structure_hash`, `cached_at`, `payload`) для хранения слепков страниц.
* **Нормализация DOM:** Прямое хэширование сырого DOM даст ложные срабатывания (из-за рекламы, таймстампов, динамических ID). Перед хэшированием DOM должен проходить **нормализацию** — удаление volatile-атрибутов (классы анимаций, случайные ID) и вырезание известных динамических блоков (таймеры, баннеры).
* **Сравнение:** Если нормализованный `current_dom_hash == previous_dom_hash` (состояние страницы не изменилось после действия), это триггерит Supervisor.

### 6. Режим TRAINING_MODE и отмена зависших задач (TTL)
* При подозрительном поведении воркера считывается флаг `TRAINING_MODE`.
   - Если **выключен**: Supervisor автоматически инжектит корректирующий промпт (например, *"Ты кликаешь впустую, попробуй scroll"*).
   - Если **включен**: задача переходит в состояние ожидания помощи от человека в Telegram-чате (HITL).
* **TTL для заморозки:** Чтобы задачи не висели вечно, если человек не отвечает, вводится TTL (например, 15 минут). После истечения TTL задача помечается как `failed` или `cancelled`, освобождая ресурсы.
* Пользователь также получает API-эндпоинт для ручной отмены (`/agent/task/{id}/cancel`).

### 7. Авторизация стрима
* Эндпоинт `/agent/task/{task_id}/stream` обязательно проверяет права доступа (Ownership). Пользователь (или tenant) может подключиться только к тем `task_id`, которые были созданы им. Это предотвращает утечку логов агента посторонним.

### Фаза 1: Инфраструктура и база данных
1. Развернуть и настроить внешний worker (например, Celery или ARQ на базе Redis) в `docker-compose.yml`.
2. Добавить таблицы: 
   - `AgentTask` (статус, владелец)
   - `AgentTaskEvent` (события для replay)
   - `ResourceDomCache` (нормализованные слепки DOM).
3. Переписать эндпоинт `/agent/run` для постановки задачи в очередь и возврата `task_id`.
4. Реализовать `/agent/task/{task_id}/stream` с проверкой прав владельца, выгрузкой пропущенных событий из `AgentTaskEvent` и подпиской на Redis.

### Фаза 2: Логика Worker и Supervisor
1. В `llm_manager.py` интегрировать сохранение чекпоинтов в `AgentTaskEvent` после каждого шага.
2. Написать утилиту нормализации DOM и интегрировать подсчет `dom_structure_hash`.
3. Реализовать триггеры Supervisor'а на основе одинаковых хэшей DOM и зацикливаний.
4. Внедрить логику `TRAINING_MODE` с эскалацией в Telegram и механизмом TTL-отмены.
5. Интегрировать `SELECT ... FOR UPDATE SKIP LOCKED` для безопасного рестарта "упавших" задач воркерами.

### Фаза 3: Обновление Frontend
1. Адаптировать клиентский код для работы с новым API: `POST /agent/run` → получить ID → `GET /agent/task/{id}/stream`.
2. Реализовать кнопку/эндпоинт отмены (`cancel`) на фронтенде.
