# Артефакты и журнал прогонов — дизайн

Решение владельца (02.10.2026): артефакты привязываются **к задаче**, а не к беседе.
Нужна история работы: что система делала, какие были ошибки, какие достижения — чтобы
она могла себя анализировать и улучшать; удачные сценарии — сохранять; на будущее —
возможность привязывать к артефактам что угодно (intent, сценарий, метрики).

Отдельная цель UI: результаты работы смотреть в правой панели («холст»), не засоряя чат.

## Что уже есть (не дублируем)

| Сущность | Что хранит | Роль в новой схеме |
|---|---|---|
| `agent_tasks` | прогон: query, status, conversation_id, owner_id | **владелец** артефактов и журнала |
| `agent_subtasks` | шаги плана: topic, status, result_output | готовый «план» → артефакт `plan` |
| `agent_task_events` | поток событий прогона (шаги, тул-коллы) | live-обновление панели |
| `execution_traces` | по вызову модели: модель, режим, длительность, ошибки, tools | метрики для журнала |
| `human_corrections`, `action_requests`, `apprentice_steps` | HITL и подтверждения | источники «ошибок/достижений» |
| `scenario_definitions` | сценарии, draft→active (утверждение) | «удачный сценарий» из прогона |
| `meta_analyst` (`run_meta_analyst`) | анализ сессий | потребитель журнала (самоанализ) |

Вывод: **метрики и ошибки уже есть** — не хватает (1) «материальных» результатов
(файлы, скриншоты, документы, ссылки) и (2) сводки-исхода прогона в виде, пригодном
для самоанализа.

## Схема

### `artifacts` — материальные результаты прогона

| Поле | Смысл |
|---|---|
| `id` | uuid |
| `task_id` | FK → `agent_tasks` (CASCADE). **Владелец артефакта = задача** |
| `conversation_id` | nullable (SET NULL) — чтобы показывать в контексте беседы |
| `kind` | `plan` \| `file` \| `image` \| `text` \| `report` \| `link` \| `error_dump` |
| `title`, `mime`, `size_bytes` | карточка в UI |
| `storage` | `db` \| `disk` \| `url` — где лежит содержимое |
| `content` / `path` / `url` | инлайн-текст / путь на диске / внешняя ссылка |
| `sha256` | дедуп и целостность |
| `origin` | `agent` \| `system` \| `user` — кто создал |
| `meta` | JSON: произвольные поля (модель, шаг, страница…) |
| `ref_type`, `ref_id` | nullable — задел на привязки (intent, scenario, subtask) |
| `created_at`, `deleted_at` | жизненный цикл (удаление — мягкое) |

Файлы — на диске: `PROJECT_ROOT/artifacts/<task_id>/<sha8>_<имя>`. Sha-адресация даёт
дедуп. В БД — только метаданные. Отдача: `GET /artifacts/{id}/content` стримом с
`Content-Disposition`; лимит размера; запрет симлинков и выхода за корень.

### `run_journal` — исход прогона (то, «что система знает о себе»)

Одна строка на задачу:

| Поле | Смысл |
|---|---|
| `task_id` | PK/FK → `agent_tasks` |
| `status` | `success` \| `partial` \| `failed` \| `cancelled` |
| `summary` | 1–3 строки: что сделали |
| `errors` | JSON-список: что не получилось (в т.ч. перехваченные исключения) |
| `achievements` | JSON-список: что получилось (файлы, факты, находки) |
| `metrics` | JSON-агрегат из `execution_traces`: длительность, шаги, тул-коллы, модели |
| `self_review` | текст/JSON — оценка от `meta_analyst` |
| `scenario_proposed_id` | nullable → `scenario_definitions`: «удачный прогон → сценарий» |
| `tags`, `created_at` | навигация и фильтры |

Это опора для самоанализа: по журналу meta-analyst ищет паттерны неудач («падает на
капче», «модель X не тянет») и удач («такой план сработал»).

### Сценарии

Новых таблиц не нужно: `scenario_definitions` уже есть. Добавляем только связку
`run_journal.scenario_proposed_id` — шаги для сценария берутся из завершённых `agent_subtasks`.

## API (минимально достаточный)

- `GET /tasks/{task_id}/artifacts` — карточки прогона
- `GET /artifacts/{id}/content` — содержимое (stream / inline)
- `GET /tasks/{task_id}/journal` — исход и self_review
- `GET /conversations/{conversation_id}/runs` — прогоны беседы (история в панели)
- `POST /artifacts` — публикация из MCP-инструмента `publish_artifact`
- `DELETE /artifacts/{id}` — мягкое удаление

## Наполнение артефактами

1. **`plan`** — из `agent_subtasks` (автоматически, бесплатно) с живым статусом шагов.
2. **`image`** — скриншоты браузера (сейчас уходят только в Telegram).
3. **`file` / `report`** — явная публикация агентом (MCP `publish_artifact`); при
   необходимости — закачка внутри контейнера (yt-dlp/httpx), а не браузером на хосте.
4. **`error_dump`** — при падении прогона: то, что раньше исчезало вместе с логами.
5. **journal** — пишется по завершении прогона (и в worker-пути, и в Telegram-пути).

## UI

Правая панель получает вкладки: **Контекст** (источники — как сейчас) и **Артефакты**.
Артефакты сгруппированы по прогонам (задачам), новые сверху. В карточке прогона: статус,
ошибки/достижения, артефакты с превью (markdown / картинка / текст / чек-лист) и «Скачать».
Во время прогона панель обновляется по SSE.

Плюс независимая правка: боковые колонки — ресайз и скрытие с сохранением состояния.

## Фазы

1. **Фронт**: ресайз/скрытие левой и правой колонок (без изменений бэкенда).
2. **Каркас артефактов**: таблица `artifacts`, API, вкладка в панели, первый наполнитель —
   план из `agent_subtasks`.
3. **Наполнение**: `publish_artifact` (MCP), скриншоты браузера, `run_journal` + самоанализ.
4. **Сценарии**: предложение сценария из удачного прогона (`scenario_proposed_id`).
