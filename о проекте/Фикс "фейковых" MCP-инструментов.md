# Фикс "фейковых" MCP-инструментов + верификация side-effect'ов

Этот план описывает шаги по устранению заглушек в MCP-серверах и добавлению механизма верификации результатов работы инструментов в аналитику.

## User Review Required

> [!WARNING]
> Верификация side-effect'ов добавляет дополнительный вызов (проверку scheduler'а/файловой системы) после каждого relevant tool call — это небольшая, но ненулевая задержка на каждый такой вызов. Механизм верификации будет гибким и настраиваемым.

> [!NOTE]
> На этом этапе агент **не блокируется и не исправляется автоматически** при обнаружении `tool_verified=False` — только фиксируется в аналитике для последующего просмотра человеком.

## Принятые решения (по итогам ревью)

1. **Persistent Jobstore**: Мы **не будем** оставлять in-memory реализацию, так как это просто отложит проблему до первого рестарта контейнера. В `scheduler_mcp.py` будет настроен `SQLAlchemyJobStore`, подключенный к основной базе `contextus.db`. Это потребует инициализации таблицы `apscheduler_jobs` (обычно apscheduler создаёт её сам, если не передать параметры, отключающие это, но мы убедимся, что это работает штатно).
2. **Безопасность (Shell Injection)**: Запуск произвольных команд по крону от лица агента — огромная дыра в безопасности. В `scheduler_mcp.py` мы введём ограничение, аналогичное `workspace.py`:
   - Крон-задачи смогут выполнять только скрипты (.py, .sh), лежащие строго внутри `PROJECT_ROOT` (используя `get_safe_path`).
   - Альтернативно/дополнительно: запретить передачу сложных шелл-команд (с пайпами `|` или `&&`) и ограничить выполнение только вызовом конкретных бинарников (например `python3`, `node`) с аргументами. В идеале мы будем вызывать `subprocess.exec` вместо `shell=True`, чтобы избежать инъекций на уровне оболочки.

## Аудит MCP-серверов

Я провел аудит всех файлов в `backend/mcp_servers/`:
- `scheduler_mcp.py`: **НАЙДЕНЫ ЗАГЛУШКИ**. Инструменты `add_cron_task` и `toggle_task` возвращают текст об успехе, ничего не делая. Будут исправлены.
- `workspace.py`: Инструмент `write_file` **реально записывает** файлы на диск (`f.write(content)`), здесь нет заглушки. Файл `price_checker.py` из инцидента действительно был создан.
- `analyst_mcp.py`: `optimize_tool_behavior` реально дописывает текст в `improvements_log.md`.
- `coder.py`: Запускает реальный подпроцесс `claude`.
- `web_stealth.py`: Вызывает методы playwright.
- `contextus_rag.py`: Записывает в БД и запускает реальную индексацию.

**Итог аудита**: Заглушки локализованы только в `scheduler_mcp.py`. В остальных местах инструменты действительно пытаются выполнить заявленные действия.

## Proposed Changes

### База данных (Models & Migrations)

#### [MODIFY] `backend/models.py`
Добавление новых полей в `ExecutionTrace`:
- `tool_verified` (Boolean, nullable=True)
- `tool_verification_details` (Text, nullable=True)

#### [NEW] `backend/migrations/versions/...`
Будет сгенерирована Alembic-миграция для добавления этих полей (с использованием `render_as_batch=True`).

### Исправление MCP Серверов

#### [MODIFY] `backend/mcp_servers/scheduler_mcp.py`
- Конфигурация `AsyncIOScheduler`: добавление `SQLAlchemyJobStore(url="sqlite:///contextus.db")` в качестве хранилища по умолчанию для обеспечения персистентности между рестартами.
- `add_cron_task`: импорт `CronTrigger`, проверка команды на безопасность (запрет `shell=True`, разрешение только путей внутри `PROJECT_ROOT`), добавление задачи в шедулер. В случае ошибки добавления — явный выброс исключения.
- `toggle_task`: вызов `sched.pause_job(task_id)` или `sched.resume_job(task_id)` с выбросом ошибки при отсутствии задачи.

### Логика Агента

#### [MODIFY] `backend/agent/llm_manager.py`
- Будет добавлен словарь `TOOL_VERIFIERS`, содержащий функции проверки для конкретных тулов (например, проверка наличия файла через `os.path.exists` для `write_file`).
- Во время цикла выполнения инструментов (или после него) будет выполняться верификация.
- Результаты верификации будут собираться и передаваться в `_record_trace`, где они сохранятся в новые поля БД `tool_verified` и `tool_verification_details`.

### Аналитика

#### [MODIFY] `backend/main.py`
- В `GET /analytics/metrics` добавится 5-й блок: **"Unverified Success"**, агрегирующий задачи, где `final_status == 'success'`, но `tool_verified == False`.
- В `GET /analytics/dashboard` будет добавлена HTML-таблица для отображения этой новой метрики с выводом `tool_verification_details`.

### Тестирование

#### [MODIFY] `backend/test_analytics.py`
- Добавление теста `test_unverified_success`: симуляция записей с `tool_verified=False` и `tool_verified=True`, проверка правильности агрегации в SQL.
