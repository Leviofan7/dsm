# Архитектурный рефакторинг: Переход от "слепого" к верифицируемому циклу агента

Ваша идея абсолютно правильная. Хардкодить селекторы — это борьба с ветряными мельницами. Добавление шага `Verify` делает архитектуру самовосстанавливающейся (self-healing), а умный фокус решает проблему "ввода в никуда".

Ниже представлен план реализации этих изменений.

## Proposed Changes

### `backend/agent/vision.py`
Добавление новой, более "легкой" функции верификации, которая проверяет результат последнего действия.

#### [MODIFY] vision.py
- Добавить асинхронную функцию `verify_action(base64_image: str, last_action: dict, goal: str) -> dict`.
- Системный промпт для `verify_action` будет просить модель вернуть JSON формата `{"success": true/false, "reason": "почему"}`.
- Модель будет оценивать: "Я сделал действие X для цели Y. Увенчалось ли оно успехом (например, открылась ли новая страница, появился ли текст в поле, закрылась ли модалка)?".

---

### `backend/agent/browser.py`
Полный отказ от слепого выбора "последнего инпута на странице".

#### [MODIFY] browser.py
- В методе `type_text` будет внедрен продвинутый скрипт (через `page.evaluate`), который возвращает `True` или `False`:
  1. Если `document.activeElement` уже является инпутом (куда агент мог кликнуть ранее) — возвращаем `True`.
  2. Фильтрация элементов: берем только те `input` и `textarea`, которые **видимы на экране (во viewport)**.
  3. Сортировка по семантике: ищем `placeholder` или `aria-label` со словами ("search", "поиск", "ответить", "reply", "message"). Если нашли — делаем `.focus()` и `True`.
  4. Фоллбэк: берем самое **крупное** видимое поле на экране (так как основное поле обычно больше скрытых).
  5. Если вообще ничего нет — возвращаем `False` (вызываем исключение, чтобы оркестратор понял, что писать некуда).

---

### `backend/agent/orchestrator.py`
Внедрение нового шага `Verify` в главный цикл управления.

#### [MODIFY] orchestrator.py
- Изменение цикла с `Observe -> Think -> Act` на `Observe -> Think -> Act -> Verify`.
- После выполнения действия (если это не `wait` и не `done`), оркестратор делает новый скриншот и вызывает `vision.verify_action`.
- Если `verify` возвращает `success: False`, в SSE-стрим отправляется диагностическое сообщение (например, "Действие не сработало: модалка не закрылась"), и оркестратор может сразу запросить у Vision-модели альтернативное действие, увеличивая счетчик неудач.
- **Детектор зацикливания**: Убедимся, что счетчик сбрасывается при любой смене URL, и что неудачные попытки `Verify` корректно увеличивают счетчик застревания.

## Verification Plan

### Automated Tests
1. **Тест неверного фокуса**: Передача агенту URL со скрытыми инпутами и одним видимым семантическим. Проверка, что текст попадает в правильное поле.
2. **Тест Verify**: Искусственный сбой клика на странице. Проверка, что `verify_action` ловит ошибку и возвращает `success: False`.

### Manual Verification
- Запуск запроса на `Duck.ai`, который приводит к ошибке сервиса.
- Ожидаемый результат: Шаг 1 -> type. Шаг 2 (Verify) -> видит ошибку и говорит `success: False, reason: Сервис недоступен`. Цикл безопасно прерывается.

## User Review Required
> [!IMPORTANT]
> Добавление шага `Verify` **удвоит** количество обращений к локальной LLM на каждое активное действие (добавляется еще один прогон картинки через нейросеть после клика/ввода). Это повлияет на скорость работы агента. Согласны ли вы пожертвовать скоростью ради системной надежности?
